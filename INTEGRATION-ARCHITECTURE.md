# Integration architecture

| Domain | Authority and representation | Compatibility, cost and validation |
| --- | --- | --- |
| Math and English | Existing curriculum engines and checkers decide correctness. Workspace tools emit supported response types and evidence. | An explicit answer may come from the skill model or applicable independent base-ten route. Read-to-me directions do not disclose the target. Target-text narration, hints and worked examples record assistance. Matched UI, exhaustive sampled routing and scored interactions cover these boundaries. |
| Drawing input | The same pointer-to-canvas helper converts client into intrinsic pixels on both candidates. Paper dimensions, gestures and history remain with their owning surface. | Scratch paper is transient. My Art keeps original marks through the existing drawing/metadata transaction; historical crayon encodings are accepted only for a replay that matches original pixels. Native and browser tests cover object storage and drawing history. |
| Original identity and PNG admission | Owner-scoped drawing ID, digest, parent and root define a logical family. A selected rig also binds the exact source hash. The family gateway authorizes the exact digest. | Stored bytes, editable source chunk, visible pixels and preview stay distinct. Truecolor suggested palettes require separate reviewed admission of the copy; the indexed palette is necessary to decode indexed pictures. Family and Adult Private guards stay at transaction boundaries. |
| Catalog and chooser | The drawing metadata index supplies discoverable records. Root traversal verifies owner and parent hash; selection carries one exact immutable asset pin. | Historical semantic labels normalize at the owner boundary. Name, revision and role can vary independently. Batch thumbnails, generated movement previews and usage discovery avoid decoding every original just to open a picker. |
| Movement and physical parts | Immutable rig versions hold source-relative piece geometry/hinges and explicit whole-picture movement. SceneEngine executes ordinary data-only code. | Presets, authored absolute points, and historical relative stops use their own version-aware execution paths. Parts retain parent and source relationships. Saved scene commands remain editable. Picture-kind arrow drafts and partial edits use the existing drafts transaction. |
| Stage registry and placements | One illustrated asset registry references the 48 original files. SceneProject stores cast, programs, world, optional layer controls and independent visual stacking. | Original percentage decorations, stage-unit decorations, pinned-picture worlds and illustrated stage-only projects remain readable. Stage rendering, screenshots and export use the same reference traversal. Numeric, pointer and fixed scenery controls operate on the chosen instance. |
| Keeping or reusing a world | CreationWorkspace selects the existing legacy or prepared IndexedDB authority. Kept revisions pin artwork and behavior. | Full world reuse uses the exact kept transaction. Scenery-only reuse keeps the target cast and its code and resolves the kept background, props and visibility. Restore and portable import validate every reference and reject corrupt or cross-owner identity. |
| Games | The private notebook holds contextual instructions and immutable game-specific bindings. Native Rally and the trusted local picture hunt have existing playable hosts. | Local Gem Hunt and the selected-slot compositor each require their scoped review mode. No general remote artwork is enabled. Copy/replacement and replay are tested separately from worker, sandbox or real-host approval. |
| Review and recovery | The permanent offline runner bundles actual source and exact assets with a synthetic storage namespace. Complete recovery uses the existing restore coordinator and its transactional sources. | The shell labels synthetic services. Original-source hashes and scoped checks survive export; corrupt or missing references cannot silently select a newer drawing. A recording or static gallery does not establish interactive recovery. |

**Rollout and rollback.** Keep original source refs and validation receipts with their writers. Use read adapters on historical entries and retain the original bytes. Introduce new features through explicit edits and new immutable revisions. The native storage authority changes only through its established preparation and reconciliation path. Before advancing a future reader, test the authorized readers in both directions on their supported records, failed migration, interrupted restore and a fresh independent target. Roll back to a compatible reader and retained recovery point if those checks fail. A release that must be readable by an older unsupported schema needs separate qualification before rollout.

**Independent programs.** The discipline for a later family release, including source and image pins that must be refreshed, is recorded in [the release handoff](RELEASE-HANDOFF.md). The master execution journal remains with that release program.
