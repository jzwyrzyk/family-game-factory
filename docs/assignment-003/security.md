# Security findings and activation blockers

## Addressed in Assignment 003

- **PEM/config mismatch:** `loadGatewayConfig` supports an explicit absolute `githubPrivateKeyFile` mounted from the existing PEM secret. It rejects ambiguous inline+file configuration, missing/non-RSA keys, and keeps existing inline configurations compatible. Gateway and owner CLI share this loader. Startup failures do not print key/config details.
- **Cross-service secret exposure:** separate config secrets and service identities; preview never mounts the PEM or session key. IAM preflight rejects runtime access to foreign secrets and unexpected project/ancestor roles. Service revisions use numeric versions, not `latest`. Existing signing keys survive reruns.
- **URL trust:** bootstrap revisions serve no private routes or dependencies. Origins come from GCP resource metadata and must be distinct canonical HTTPS Cloud Run hosts. No speculative hostname, arbitrary input URL or health redirect is accepted.
- **Readiness gap:** both final services probe persisted state; preview health rejects wrong-host requests. The Cloud Run TCP startup probe does not prove application readiness; the deployment's HTTPS health checks must pass too. Bootstrap reports `ready:false`.
- **Accidental activation/deployment:** offline default plan; explicit execute switch; immutable registry digests; unknown/active-service refusal; disabled paid config; no deploy/dispatch workflow added; no change to the worker tag or frontend. Full gVisor verification rejects skips and partial tests.

## Must resolve/review before real activation

1. **Firestore IAM scope:** `roles/datastore.user` (gateway) and `roles/datastore.viewer` (preview) apply to the existing project's databases, not just `family-001`. Preview is read-only but can read more than one workspace if more exist. Firestore server IAM bypasses browser Security Rules. These predefined roles are the supported baseline, not a claim of document-level isolation. Review existing project/database contents, client rules and any unrelated tenants; use dedicated database/project isolation or a reviewed narrower supported policy if required. Do not silently grant Editor/Owner to fix access.
2. **IAM audit limits:** direct project, visible ancestor and secret policies are checked. Group membership, external federation, service-account impersonation, deny policies, domain policies and all inherited/operator access are not proven by these checks. Review who can impersonate the runtime identities, deploy revisions, access secret versions or write the registry. Metadata-read denial blocks deployment. A policy check is not a live permission probe; actual service health checks exercise database access only.
3. **Preview capabilities in URL query strings:** existing preview links use short-lived query capabilities. Cloud Run/load-balancer/request logs can retain query strings. Before any real private artifacts are served, implement/review application/logging exclusion or a safer capability-delivery flow. Disabling app console logs alone is insufficient. Do not paste preview URLs into issues or evidence. Inactive health checks contain no capability.
4. **Invitation abuse protection:** existing one-use sessions still need reviewed edge rate limiting and target-browser CHIPS/same-site testing before public admission. No invitations or allowance are created here. Public health reads also consume database resources; include them in rate/abuse controls. Verify direct Firestore client access is denied.
5. **Full isolated browser smoke remains unpassed:** the prior workspace lacked sufficient disk for the browser image. The strict verification wrapper checks existing worker fixtures, gVisor enforcement, desktop/mobile/replay/no-egress and hostile source outcomes. No host/runc fallback. The verification wrapper rejects modified or untracked worker source/test inputs. Use an approved credential-free ephemeral runner and review the evidence. Deployment is permitted only inactive; activation remains blocked until this passes.
6. **Workflow trust and budget:** verify App Actions-write/Contents-read permissions on this repository, numeric installation/repository IDs, protected exact worker tag, generation/sandbox environments, OIDC binding, image digest and absence of secrets in the test job. Keep repository `FACTORY_ACTIONS_APPROVED=false`. It could not be read with this connector (403); owner must verify. The original worker tag is preserved, not moved to this deployment PR's SHA.
7. **Container supply chain:** deployment images are digest pinned, but existing Dockerfiles use the moving `node:22-bookworm-slim` build base. Rebuilds are not byte-identical. Review/pin an approved base digest and image/SBOM scan as part of release policy; no unverified base digest is invented here. No host credentials enter the builder context. Runtime packages still include tooling; reducing images is separate work.
8. **Operational policy:** review region/data residency, log retention, secret rotation, data export/deletion, quotas, budgets/alerts and retention/orphan cleanup before children use a real service. Request billing/min-zero/max-one reduces idle/parallel exposure but is not a total spend cap. GCS artifact storage, scheduler and model invocation are intentionally unconfigured.

No account recreation or additional API funding is required by this assignment. Existing project/service accounts/App/secret are inputs, not evidence that their IAM or deployed services have been verified in this workspace.
