## Diagnostic clarification and next acceptance

`inspect_build_status.mjs` prints bounded status fields from the live configuration and durable job state. Its first version compared `qualityRequired` to boolean true, but the source stores the policy string `game-quality-v1`. The boolean display is corrected; the earlier false value is not evidence that production quality policy was disabled. This is a diagnostic-output correction, with no gateway behavior change.

The read-only helper exposes `lastStoredRepairFindings`, restricted to the fixed allowlist of quality-finding enums in the saved sanitized feedback's `FINDINGS` field. Unknown values, free text, malformed fields and findings without valid previous-attempt provenance are omitted. `lastStoredRepairFromAttempt` identifies which prior attempt supplied that feedback; a final failure may retain an earlier repair's findings, so these fields do not independently diagnose the terminal attempt. `testReportPresent` and `reviewReportPresent` indicate stored report-fingerprint presence, not raw report contents or a passing verdict.

The helper separately accepts an optional producer-written `execution.lastFailure` record: the last rejected stage (`test` or `review`), its own zero-based attempt, exact category/code enums, at most twelve unique quality findings, and optional four-axis review statuses (`pass`, `fail`, `not-tested`). Malformed or absent metadata yields `lastFailure: null`; extra raw fields are never emitted. A test-stage record cannot carry review axes, and a recorded attempt cannot be later than the job's current execution attempt. This is **last rejection history**, which can remain after Ready or cancellation, not an inferred terminal error. Older jobs without this producer record cannot have terminal details reconstructed by the reader. The `lastStoredRepair*` fields retain their separate prior-feedback provenance.
