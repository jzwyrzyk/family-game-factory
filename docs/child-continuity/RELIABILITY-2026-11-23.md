A broader implementation must first specify an owner-approved retention policy, versioned schema, transaction/recovery model, export format, compatibility floor and rollback plan. Test process termination at every journal boundary, large/old content, concurrent ownership changes, quota at each store, remote uncertain outcomes, and exact backup/restore bytes before rollout. Cloud activation requires separate operational authorization. These open F06 items do not authorize dropping data and are not represented as completed by PR123.

## Staged release and rollback

1. Preserve a verified parent backup and existing operational rollback/receipt records. Validate the target reader against actual schema fields; never delete unknown fields to make an older bundle load.
2. Deploy a compatible gateway separately, verifying private coach contracts, authenticated request lookup, conservative paid settlement, fixed worker leases and old callback compatibility. This task does not perform that deployment.
3. Release any private-worker transport change only through the independently reviewed immutable public-source pin/private workflow process. The source PR does not repin it.
4. Publish the frontend only after backend compatibility and rollback are verified. Coach v2 requires its matching gateway/private coach and selection-aware compiler; reliability adds retained chapters, notification metadata and durable pending identity requirements.
5. Run separately authorized Adult Build → Review → Play → Keep → Reload and real-provider/device acceptance. Fixture CI does not establish live model quality, billing, physical-device behavior or child comprehension.

Drain old gateway and worker in-flight operations before a backend rollback: older completion code lacks reservation-identity fencing and older coordinators ignore fixed leases/report receipts even if JSON preserves those fields. Do not mix old completion writers with erased/reused receipt identities. A new gateway remains wire-compatible with the pinned old worker, but that does not install the new worker transport/retry behavior.

Keep the new compatible readers during a frontend repair rollback, or prove a lossless migration preserving every original record and pending identity. Restoring an older backup is a separately chosen recovery action with an explicit cutoff, not a claim to preserve work created after that backup.
