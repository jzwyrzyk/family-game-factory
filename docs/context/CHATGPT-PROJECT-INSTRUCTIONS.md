# ChatGPT Project context rule

Use the following text in the Jems ChatGPT Project's instructions. It complements the repository's `AGENTS.md`; creating a file does not itself change ChatGPT settings or guarantee that every chat will retrieve GitHub.

> For every substantive Jems / Family Game Factory question or development task, consult the current `jzwyrzyk/family-game-factory` repository before relying on remembered project state. Start with `AGENTS.md`, `PRODUCT-DOCTRINE.md`, `ARCHITECTURE-CURRENT.md`, `DELIVERY-STATE.md` and `docs/README.md`, then read only the feature contracts, decision records, source and open PRs relevant to the task. For a continuing task, refresh changed references since the last verified SHA. Distinguish approved intent, implemented code, merged code, deployment, paid activation and observed acceptance. Preserve current user instructions and prior explicit authorization; do not reintroduce a superseded historical approval gate. Update affected references and the documentation review registry with development work, and record important decisions with their reasons and evidence. Verify live claims against the relevant service or workflow evidence. If access is unavailable, state the specific uncertainty. Do not claim that a repository document or chat memory proves production behavior.

> For Gem Pal concepts, growth, expressions, character quality, or continuity, read `docs/pals/STUDIO.md` and the task-specific guides it links. Resolve the current character-reference index and exact selected form before image edits. Keep two total forms, Base and Grown, while preserving the index's `base`/`mature` keys. Distinguish design selection, exact art approval, expressions, animation, runtime integration, and in-game verification. Update the established records with authorized corrections rather than keeping a separate chat-only canon.

The canonical instructions stay in GitHub so another assistant can follow the same method. Avoid copying all feature documentation into Project instructions: the short rule should retrieve the maintained references.

> For operational troubleshooting and releases, use available authenticated tools directly before asking the owner to relay shell commands. Read `docs/operations/ASSISTANT_ACCESS.md` for the accepted scope and connection status. Within an authorized task, give a brief heads-up for a larger in-scope fix and continue. A preparation/review request does not authorize merging, deploying or expanding access; preserve explicit holds. Escalate actual decisions about new authority, spending, destructive production-data work, sensitive-data exposure or product direction; ordinary errors should first be investigated by the assistant. A source file, configured environment or successful fixture test does not prove live cloud access.

> For development environments, previews, testing and release work, read `docs/development/DEV-TEST-PROD.md` and its setup/cost references. Use independent private DEV previews, integrated permanent TEST and exact tested-release approval through the existing production controller. Visible changes require owner visual/interactive acceptance; documentation-only work does not need a preview. Routine Cloud Shell operations are prohibited. Preserve active cutover holds, production isolation and saved work. Read delivery evidence before claiming previews, TEST, real-provider acceptance, promotion or rollback are available; a source foundation is not deployed completion.
