# Gem Pal Studio — repository-owned design method

**Status:** Accepted operating method and creative scope; implementation and delivery evidence remain separate.
**Recorded:** November 19, 2026 (America/New_York).
**Decision source:** the owner requested a reusable guide capturing Gem Pal inspiration, Base/Grown development, continuity, story, gem anatomy, and recurring quality corrections, then explicitly authorized a repository PR and merge. This record paraphrases that instruction; it does not publish private conversation transcripts.

## Context

Parallel character conversations produced useful approvals and corrections, but a remembered name or a recent render could point to the wrong variant. Decorative growth sometimes preserved too much of the original body, while expression edits sometimes changed anatomy. The owner needs a reusable method that improves the starting brief and catches avoidable failures before review.

An account-level skill alone does not make the method available to repository work. Copying its private source locators or a frozen approval table would also create an unreliable second character catalog.

## Decision

- Keep the canonical method in [Gem Pal Studio](../pals/STUDIO.md), with focused doctrine, growth, quality, continuity, and prompt guides.
- Route repository assistants through `AGENTS.md`, the documentation index, and a [thin repository skill](../../skills/gem-pal-studio/SKILL.md). Provide the equivalent retrieval rule for ChatGPT Project instructions without claiming those settings were automatically changed.
- Preserve two total visual forms, Base and Grown, with one transition. Require purposeful gem anatomy and meaningful structural development that remains recognizable as the same character.
- Reuse the established character-reference index from the separate artwork workstream; preserve its `base`/`mature` keys and selected-reference history. Do not create another populated registry or infer current approvals from this method.
- Keep exact asset identity, design selection, expression approval, animation compatibility, runtime integration, and observed in-game behavior distinct.
- Capture corrections at their proper scope, retain superseded variants, and update affected references with each authorized development change.

## Consequences and limits

This method makes the project instructions portable and reviewable. It requires actual reference inspection and explicit handling of missing evidence. It does not retrain an image model or guarantee an acceptance rate. Template records are empty scaffolds, not approved art or a runtime schema.

The artwork index and companion implementation remain separate workstreams: [PR74](https://github.com/jzwyrzyk/family-game-factory/pull/74) and [PR68](https://github.com/jzwyrzyk/family-game-factory/pull/68). This decision does not merge those drafts, set numerical growth thresholds, rename saved data, or deploy a feature. Later explicit owner decisions can change artistic scope; reconcile them in the actual character record and relevant guide.

## Evidence and maintenance

The guide incorporates the saved design methodology and character-specific feedback in paraphrase. Its initial repository baseline and source-index fallback are recorded in [Studio](../pals/STUDIO.md). Quality gates are editorial checks, not a validated creativity score; the reaction vocabulary remains proposed until separately selected.

Use the existing [maintenance process](../context/MAINTENANCE.md), documentation checker, and `pal-design` review area. Record merge or release evidence in [delivery state](../../DELIVERY-STATE.md); a merged document does not establish a deployed companion system.
