## Household browser transfer

The transfer copies reviewed localStorage keys and IndexedDB stores. It preserves key paths, indexes, record keys, blobs, typed arrays and dates. A review gate stops on unfamiliar Jems keys or unsupported database types. The original source stays available. Browser credentials, cookies, sessionStorage, cache entries and unrelated origin records do not belong in a recovery file. The recovery file contains private child and adult data in readable form. Use owner-controlled encrypted storage, restrict access and remove the temporary copy on the approved retention schedule. Transfer each original browser partition to its matching empty destination browser. Do not merge devices.

1. The release engineer prepares a private mapping with the exact original owner family ID, original workspace, source origin, target owner origin and original gateway. Record the tested server backup fingerprint. Run the read-only binding check against the existing private workspace. If data is missing, any row belongs to a different family, or a ledger reservation is outstanding, resolve it before continuing.
2. While the original origin is still accessible, stage its dedicated **household-transfer** directory. Generate that directory with `node scripts/beta/prepare-source-transfer.mjs reviewed-source-map.json empty-directory`. Stage it on the original site at a path that also serves its module files. This separate, temporary directory asks for the existing guardian passphrase through the trusted original gateway. Existing Pages and third-party cookie restrictions can prevent original-device verification. Retain the original device and use an approved temporary same-site handoff or existing trusted browser partition if it cannot verify. Test this before switching DNS or retiring Pages.
3. Close other Jems tabs on every participating device. On the old origin open **Move this household’s workshop**, verify the parent passphrase and privately save the file and fingerprint. On the new IAP-protected household host, visit **/household-transfer/** before opening Jems on that device. Select the file and **Restore and verify**. Compare the displayed fingerprint, counts and representative saved activities with the source. The destination refuses unrelated or occupied storage. If interrupted, use the same file to resume. **Remove partial copy** removes only matching, journaled writes. Concurrent or altered destination work stops the operation.
4. With the original writer paused and no reservations outstanding, the authorized operator applies the confirmed server binding once. Use the existing workspace and artifact prefix in place. Set the same `householdBudgetBinding` on the original household gateway before enabling external participation. Verify signed household device and Adult Private records still match the original family, and check the same month's ledger opening balance. Re-enroll new-origin devices using the ordinary trusted-device procedure. HttpOnly device credentials cannot be copied between origins.
5. Preserve the original data and original runtime revision through acceptance. The new host must receive no other household or invited family's local data. At network or authorization failure, keep backups and leave the release pending. Restore-test before any irreversible deletion or old-environment disposal.

The server helper defaults to an explicit read-only invocation. Run `node --import tsx scripts/beta/household-binding.ts --check reviewed-binding.json` using the approved operations identity. The reviewed file contains projectId, artifactBucket, binding with environment, familyId and workspace, and testedBackupDigest. After signed approval the same helper takes `--apply reviewed-binding.json bind-EXACT_WORKSPACE`. It verifies ownership, reads the full chunk/artifact format, and coordinates the opening balance in a single Firestore transaction. A repeated identical mapping does not double-count. A different binding fails. The tool logs only operational counts and the named mapping.

It retires only matching shell caches and navigates controlled tabs to the welcome page. It preserves household localStorage and IndexedDB. Retire the temporary transfer directory after checking every mapped owner device.

Revocation takes effect on the next successful protected request. An old public service worker receives its retirement script only when the browser reconnects and updates. Keep clients offline during a drill, reconnect them and verify that historical private data never appears on another family's origin.

## Stop and rollback

The operator can immediately pause invitations and participation, set the global spending stop, suspend affected families and revoke individual trusted devices. Observe outstanding job reservations and settle authenticated callbacks conservatively. Keep the shared ledger and ownership protections in the rollback runtime. Block new requests before rerouting. Re-enable the previous authenticated compatible revision only after checking its ability to read all records and enforce the shared stop.

Before destination writes, use the original quiescent household and known private runtime plus the retained rollback copy. After new writes exist, freeze both writers, export those records and reconcile from the latest recoverable snapshot on an isolated restoration target. Pointing back to an older snapshot can lose post-cutover edits. Never return a private application or family content to public Pages. Completed erasure and expired backup retention can be irreversible. A signed privacy case, verified backup policy and independent confirmation precede those actions.
