# Private pictures in 2D game ideas

From My Art, choose a picture, select its role and choose **Make a game with it**. From Invent or an existing game's tools, **Use my art** returns the selection to that same notebook. A short local question asks about the action or consequence. The answer, name and exact picture version stay in the local plan. A second picture chosen for an occupied role asks for explicit replacement. Removing it from the plan preserves earlier tests.

The implementation is stacked on application #213, including the shared library and the #206 qualified review renderer. The #202 compositor and #212 Gem Hunt host are parallel review fixtures. The normal application saves plans. Online art-bound construction and retry stop before spending admission. Prior admitted work can still reconcile through its original job identity. The offline review build has two fixed, locally packaged sample programs and four hand-authored synthetic images. Only this build offers sample play. The source checker and esbuild compile the reviewed fixture. The runtime supports eight images including the background. It exercises the archived generated-module-v2 engine. The fixture source defines flight, pickup, obstruction and the goal. It has no model call, remote job or reward authority.

## Binding protocol

1. My Art uses Workstream D’s shared catalog to pass its logical original ID and hash, exact drawing ID and digest, optional semantic identity, name and selected role to the trusted host. The existing owner notebook stores the plan. One picture can occupy several slots. A review test snapshots the pins, its parent and the SHA-256 of its complete immutable program document. Keep moves a separate pointer after a completed round.
2. The host chooses a saved test from the current game and profile on the current origin. During asynchronous resolution it rechecks scope and the full test. Each lookup reads one selected original by ID from the existing art store, verifies owner, byte hash and bounded dimensions, and rejects missing data. Historical uses allow archived originals. A failed lookup never opens the frame.
3. The review build requires each selected byte hash to match the four checked-in synthetic originals. It verifies the program document digest and uses the reviewed premium runtime archive. The host opens a fresh scripts-only, opaque iframe and uses the shared review encoder to strip editor history and metadata, then delivers only visible pixels in memory to its fixed bootstrap. Delivery targets the specific frame after load. Replies bind to the frame window, opaque origin, fresh channel and artifact. Each new run has a fresh context. This path only accepts a reviewed program bundled at build time.
4. The trusted frame can inspect, decode and retain the delivered images for the life of that frame. Its generated worker receives game-local draw handles and aspect ratios. It has no image bytes, drawing IDs, owner identity, names, hashes, URLs or storage client. The archived command validator bounds draw commands to the declared handles. Position, proportional scale, rotation and runtime movement use the existing renderer. Prepared flips apply through the chosen My Art version. The fixture has no general rig adapter.
5. Replay resolves the same pins. Profile/page changes tear down the frame, listeners and input. Reopening checks authorization and bytes again. The program restores missing-art errors through My Art. Kept and earlier tests remain selectable through later changes, notebook save, supported copies and complete recovery. There is no second image library or raster cache in the notebook.

The restricted family entry, private worker, generation request schema and production viewer have no new delivery route. Do not give the generated artifact a bearer URL or private catalog. A hosted design must bind the authorized family, profile, game revision, artifact digest, slot manifest and current consent to a short-lived grant with replay and revocation controls. Child pixels in gameplay captures would also reach premium visual review under the current provider design. That path requires isolation before any hosted trial. The synthetic per-frame allowlist is insufficient evidence for delivery of real family artwork.

## Run the local review

Use the repository’s locked Node dependencies and a Playwright Chromium installation. Set `CHROMIUM_PATH` if using the system Chromium.

```sh
npm run test:game-art
npm run build
```

To play manually, serve `test-results/game-art-build` on loopback after the first command. Start at `?art=1`. Import [the rocket](../../tests/game-art/rocket.png), [rock](../../tests/game-art/rock.png), [dragon](../../tests/game-art/dragon.png) and [valley](../../tests/game-art/world.png) through My Art. Choose Main player, Collectible and Obstacle, Other character, and Background respectively. Select **Try art in a sample game**. Fly right to collect, fly above or below the obstacle, and reach the right edge. Keep the test, try faster flight, and reopen the first test. Without a selected background the fixture uses the approved Gem Factory workshop.

The dedicated configuration supplies the reviewed program archive. Ordinary Vite, restricted family and offline app builds receive no fixture archive or runtime delivery UI. The test suite also runs under the existing generated-art CI command.

| Boundary | Evidence or remaining gate |
| --- | --- |
| Local pixels and gameplay | Browser compares the full initial canvas against a direct composite of all five selected images. Ordinary input, collection, collision, Keep, changed flight speed, reload and replay exercise the actual frame. Captures are from synthetic play. |

| Deployment | Application source review only. Production delivery, worker repin, paid calls and external family activation require their own evidence and authority. |
