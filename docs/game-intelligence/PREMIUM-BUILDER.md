# Adult Private premium game builder

The [November 26 activation package](premium-benchmark/NOVEMBER-26.md) describes the separately configured premium test ceiling, proposed one-repair envelope and owner decisions. Merged PR139 supplies the disabled foundation. Its [completion handoff](premium-benchmark/COMPLETION.md) retains the original offline and packaging evidence.

The owner selected `adult-astra-high-v1` to improve execution of each child's agreed idea. The pilot is a separately approved policy inside the existing builder. A chat turn, readiness verdict, model suggestion or source merge cannot submit a paid job. Build still needs the creator's explicit action, authenticated family/profile, trusted device, current permission and available allowance. ## Stage contracts

| Stage | Model or executor | Responsibility |
| --- | --- | --- |
| Conversation | Existing separately approved coach | Resolve material choices, preserve the child's own decisions and distinguish accepted helper suggestions. |
| Plan | Independently approved planning model, initially `gpt-6.2-sol`, high | Bind a bounded design specification to the exact Build request and verified base. Cover player action, visible consequences, purpose, world, characters, appearance, mood, controls, progression, feedback, recovery and payoff. |
| Art | Existing approved assets, with optional separately approved image producer | Keep existing art through gameplay edits. Compose scenery, actors and interactive objects as separable layers with clear hit targets. Pixel, flat 2D, illustrated, dimensional and realistic treatments share the same craft standard. |
| Construct | `gpt-6.2-astra`, high | Implement the chosen behavior in the approved v2 runtime. Return bounded source and ordinary player-input suggestions. |
| Exercise | Credential-free sandbox | Compile, run desktop and touch paths, observe action and consequence, inspect pause/restart and capture the rendered states. Keep authored intent probes independent of the generator. |
| Review | Independently approved review model, initially `gpt-6.2-sol`, high | Examine captures and input receipts against the original intent and proposed specification. Score visual, intent, gameplay and input separately. Source, a terminal flag or a shifted pixel cannot establish an unobserved mechanic. |
| Repair | `gpt-6.2-astra`, high | Use bounded failure findings and available evidence to correct the candidate. Preserve working behavior and approved assets. Each new candidate must pass testing and review again. |
| Preview and choose | Existing signed preview and version service | Only a fully passing candidate can become Ready. Preview stays isolated. The creator can Keep, Undo or Fork through the existing immutable revision path. |

The policy selects its stage by trusted operation. A failed Astra call never selects Sol, mini, extra-high, Max, Pro, or another coding setting. Planning and review approvals cannot override the coding model. A missing capability, stale approval or exhausted allowance produces a recoverable job/admission failure. The previous kept game and saved idea remain available. Deterministic edits use the current local handlers. Previously saved native and generated v1/v2 games retain their runtime identities. A premium edit of a generated v1 base cannot satisfy the v2 capture contract and must stop before spending. The legacy policy retains its existing v1 editing behavior. After disabling premium, a premium-origin revision or its fork remains playable and recoverable. Its next paid edit requires premium approval so rollback cannot route a code repair to a legacy model. Required Math and Language work stays with the trusted host.

The [stage-policy validator](../../server/agent/model-policy.ts) enforces the coding identity and limits. The [Responses agent](../../server/agent/openai.ts) selects the policy for the current operation. The [job service](../../server/pipeline/service.ts) handles admission and status, the [coordinator](../../server/actions/coordinator.ts) checks private worker claims and reports, and the [quality verifier](../../server/quality/game-quality.ts) binds judgments to the tested artifact.

The sandbox also bounds syntax complexity, frame work and runtime APIs. | Reasoning headroom is separate from emitted source capacity. The runtime limits still apply to every candidate. Code-native animation, independently moving actors and approved assets can fit within these limits. Unsupported mechanics stay unverified. |
| Optional image production requires a separate approval and permits at most two new raster assets per plan. | Image count alone cannot establish composition, feedback or play quality. The completed planning stage can incur a measured charge. The creator's original choices remain intact for recovery.

## Spending, receipts and privacy

Every premium stage requires an approved model identifier, high reasoning setting, supported token bounds, reviewed prices and current access/privacy approval. Keep provider credentials solely in the existing private worker. The request uses the Responses API with structured output and `store:false`. The owner must establish eligibility for the actual project, models, modalities, request parameters and retention configuration before activation. A configuration flag or fixture response alone cannot establish Zero Data Retention.

Reserve input at the full approved input price and reserve the complete allowed output, including hidden reasoning. Reserve the first plan, construction and review plus the authorized repair count with the replanning/review and image capacity they could consume. Compare that total with the explicit private premiumMaxJobMicroUsd ceiling and transactional family allowance before dispatch. Static validation requires room for each stage’s minimum instructions and schema, including at least four captures for review. Each stage also checks the actual request, image count and remaining units before transport. A larger saved source or a longer evidence packet can still be rejected under a valid configuration. A routine repair can reuse the bound plan and art. An image repair may need a new plan. Unused capacity is released on known settlement. With no conclusive usage after a paid POST, preserve conservative accounting and recover the durable job by ID. An acknowledgement loss or duplicate report must never trigger another paid attempt.

For example, at all stage maxima, Sol planning and review each reserve $0.288. Astra construction or repair reserves $1.792. With one repair and no art, the whole-job maximum is $4.736. The legacy gateway cap remains at most $1. New premium admissions require an explicit integer cap of at most $5 with the premium switch enabled. An invalid or absent premium ceiling blocks new premium jobs while durable jobs retain their original reservations. See the [proposed trial budget](premium-benchmark/NOVEMBER-26.md#proposed-first-trial).

An authorized Adult Private operator reads `modelPolicy.configuredVersion` and `activeVersion` through the existing `GET /v1/builder/status`. Read these alongside availability and its reason. Insufficient allowance or an unavailable approval yields `activeVersion: null`. A requested but invalid configuration reports `MODEL_POLICY_UNAVAILABLE` and refuses new paid work. A selected active route establishes admission readiness at the time of the read. A provider response requires its own receipt. The existing authorized `GET /v1/jobs/:id` gives the job's policy version, completed stage receipts, repair count, review status, safe error code, measured text cost, separate image allowance, reservation, accounted amount and usage uncertainty. Successful stage receipts identify stage, attempt, model, effort, input/output usage and assessed cost. A rate limit, inaccessible model, exceeded input limit or incomplete response has a bounded failure category. Provider deadlines and explicit cancellation use the safe categories `PROVIDER_TIMEOUT` and `CANCELLED`. An interrupted paid request with unknown usage requires reconciliation. Provider failures never trigger silent code-model substitution or automatic paid replay. Reasoning tokens are a subset of output. Charge that output once. Record the separately approved flat image allowance as each image validates. If a later image request is interrupted, the completed charges remain known and the outstanding request can be marked uncertain. Distinguish measured usage from a conservative settlement where provider usage is unknown. Keep private prompts, model reasoning, transcripts, keys, drawing bytes and private captures out of browser diagnostics, public release receipts, benchmarks and logs. Only synthetic fixtures are checked in. Raw captures retain the existing private artifact-store lifecycle and retention rules. No new storage migration or retention policy is implied.

## Comparative benchmark

The [paired benchmark](premium-benchmark/README.md) uses seven synthetic concepts with the same intent and acceptance criteria for both routes. The fox case requires the chosen jump and duck, 100 leaves and a visible celebration. The other cases exercise movement and levels, pattern play, construction, navigation, expressive play and an animated payoff. `npm run benchmark:premium` produces the comparison manifest. `npm run benchmark:premium -- --mock` exercises both policy routes through the real adapter and a synthetic transport. The documented fixture mode drives a checked-in authored game through the local browser worker. Its screenshots and ordinary-input receipts demonstrate the evidence pipeline on that fixture only. The benchmark can generate a blinded, printable review sheet for an authorized matched pair. The [extended capture test](../../tests/premium-capture-browser.ts) separately exercises a longer premium plan on desktop and emulated touch. Run the paired analysis with trusted per-job receipts and independently scored 1–5 reviews when a funded comparison is separately authorized.

Real model outputs, separate provider latency, actual billed cost and quality improvement across the concepts remain unmeasured. An owner's rubric can assess fun potential. Estimating children's enjoyment or educational efficacy requires its own study.

## Post-cutover activation and rollback

The following sequence is for a future authorized release. Keep the premium policy off during the current cutover.

1. **Establish the baseline.** Confirm the current production release completed and stabilized. Record verified Pages source, serving gateway/private coach/preview revisions and traffic, private workflow SHA, effective source pin, sandbox digest and trusted runtime hash. Check the trusted adult device, permissions, in-flight job identities, saved revisions and rollback targets. Retain the current legacy configuration privately.
2. **Verify access and privacy.** In the intended Adult Private provider project, verify both exact model identifiers, Responses API strict JSON Schema and high reasoning support. Verify screenshot input on review and evidence-based repair, supported caching/tier settings, privacy approval and effective ZDR eligibility. Use the existing authorized administrative access. Stop if effective project eligibility, model access, pins or evidence remain unavailable.
3. **Verify affordability.** Review current official input, cache and output prices for each stage and optional art. Calculate the whole-job reservation at the exact stage ceilings, planned repair count and image approval. Confirm the unchanged family allowance, per-job cutoff, bounded deadlines and capacity can admit the chosen UAT. A failed comparison blocks admission. Any later allowance increase is a separate spending decision.
4. **Roll out compatible binaries with premium off.** Build and attest the reviewed sandbox/runtime and private-worker artifacts. Stage a backward-compatible gateway supporting both old and new job readers, authenticated claims and report shapes. Verify a legacy flow on the currently selected worker. Release the matching private worker and credential-free sandbox through their existing change controls and verify their effective identities. Test rejection of a mismatched worker. Preserve old receipts and reads through the rollout. The coach and frontend have no new model or privileged controls.
5. **Enable the pilot separately.** Use the existing owner-approved private generation controls, the reviewed premium settings and matching private-worker identity. Scope the pilot to a trusted Adult Private profile with live generation permission. Verify the read-only status on that profile, the legacy child-facing behavior and pre-spend rejection on bad or unavailable configuration. Record the policy identity and activation time separately from the deployment receipt.
6. **Run one funded UAT.** With explicit budget approval, submit one synthetic game concept through the normal adult Build path. Follow its durable ID through sandbox, review and any bounded repair, then Play, Keep and Reload on desktop and touch. Check stage receipts, token/cost settlement, measured duration, visual captures and actual interactions. Confirm failure/reconnect and a prior version can be recovered. Reconcile ambiguous charges before another paid run.
7. **Compare matched concepts.** Run the benchmark within the authorized remaining allowance and calibrated human review. Include unsuccessful submissions, repair attempts and missing evidence alongside accepted games. Compare rate of acceptance, observed fidelity, timing and cost per accepted game. Retain synthetic evidence and aggregate results only in public reports.
8. **Exercise rollback.** Disable premium admission first. Inspect in-flight jobs and stop or drain premium work under the existing cancellation, timeout and accounting rules. Reconcile uncertain paid stages without replay. Keep compatible gateway/job readers in service until outstanding claims, reports and pending admissions settle, including late callbacks. Restore and verify the previous approved generator for a fresh authorized adult request. Retain gateway, worker, sandbox and preview readers that understand saved v2 production plans and evidence while those artifacts exist. Disabling policy selection can restore legacy generation independently of reverting readers. Match exact worker source, sandbox and gateway identities before any binary rollback. Verify saved premium and older v1/v2 revisions still play and Keep/Undo/Fork remain usable.
9. **Decide audience separately.** Record the owner decision and remaining observed quality, cost, reliability and device gaps. Moving beyond Adult Private requires a new audience decision with the applicable family consent, child privacy, spending and release evidence. The pilot policy cannot select normal child profiles. For a later child rollout, verify OpenAI's age-specific data requirements, including ZDR before processing personal data of children under 13 or the applicable digital-consent age.
