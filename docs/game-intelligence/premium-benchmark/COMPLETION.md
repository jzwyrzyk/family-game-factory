## Latency and scheduling

The full path is queue → worker setup → planning → artwork/reuse → construction → assembly → sandbox startup → technical gameplay → captures → review → optional repair/retest/review → preview. The authored benchmark records separate transport marks and sandbox setup/play/capture timings. Its calls are synthetic; no measured real model, image provider, cloud queue or invoice latency exists. Pure local compilation/extraction overlap previously saved only fractions of a second and does not justify production scheduling complexity.

The SQLite fault experiment complements the existing serial/overlap sealed-contract prototype: both completion orders join to the same hash; unknown dispatched work is not replayable after restart; cancelled or incomplete joins fail. It does not establish a distributed production implementation. Paid calls remain serial. Additional concurrency is deferred until meaningful measured provider latency benefit, Firestore accounting/recovery/cancellation and explicit authorization exist. Under 8 minutes first pass, under 15 repaired and over 80% first-pass acceptance remain hypotheses. Sandbox play alone can consume several minutes at the 7,200-tick horizon on both devices.
