# Integrated TEST infrastructure through GitHub

This is prepared source, not an installed or authorized infrastructure lane. It reuses #226's `integrated_test_stack.py`, Terraform 1.13.5/provider lock, ordered stages, HMAC-bound approval receipt, one-hour approval expiry, fresh full-plan comparison, destructive-action rejection, write-ahead marker and post-apply readback. The [coordinated release package](RELEASE-EXECUTION-2026-11-28.md) owns setup costs, administrator inputs and approval. Static DEV/TEST deployment automation remains unchanged.

## Fixed execution boundary

`Jems integrated TEST infrastructure` (`jems-test-infrastructure.yml`) dispatches only from current protected main, in the canonical public repository, on the first attempt. Its transport checks the exact workflow identity, source and current remote main before cloud access. It never checks out or executes a PR with privileged credentials. No default operation applies infrastructure: `observe` is the default; `plan` saves a reviewable plan; `apply` requires the exact attempt and approval SHA256.

The proposed WIF provider is `projects/1092405124984/locations/global/workloadIdentityPools/jems-nonproduction/providers/github-test-infrastructure`. Its approved attribute condition must bind this repository's numeric IDs, protected main, exact workflow and the corresponding GitHub environment. `jems-test-infrastructure-plan` uses `jems-test-infra-plan@jems-jzw-nonprod.iam.gserviceaccount.com`; `jems-test-infrastructure-apply` uses the separate `jems-test-infra-apply` account. Both GitHub environments must restrict deployment to main; apply requires an independent required reviewer, prevention of self-review and no administrator bypass. No ordinary static deployer receives infrastructure-administrator roles.

The planner may observe the exact TEST resource classes and operate its private state/lock objects; it must have no resource-creation or IAM mutation authority. The executor receives only the administrator-reviewed TEST setup delta. Actual role/condition definitions and effective-permission readback are required setup evidence, not inferred from the service-account names. The runtime verifies short-lived action-generated external-account credentials and exact service-account impersonation, never user ADC or a service-account key.

Private environment inputs are `TEST_STACK_VARIABLES` (the existing stage/edge/worker/release/funding contract as JSON) and `TEST_IAP_OAUTH_SECRET`. Provider credentials, adult identities and private configuration are not workflow inputs or public artifacts. The OAuth value remains an ephemeral Terraform input. Only bounded status, resource addresses/actions and approval digests reach public logs; raw Terraform output, state and plan files do not.

## Durable state and failure behavior

One new private bucket, `jems-jzw-nonprod-integrated-test-state`, must exist in `us-east5`, under project number `1092405124984`, with uniform bucket-level access, enforced public-access prevention and object versioning. These are verified before use. Its cost and IAM delta belong in the same setup approval. Existing static Terraform state is neither adopted nor moved.

The transport supplies a fixed native GCS backend at `terraform/default.tfstate`; Terraform's own lock and intermediate state updates survive runner loss. A separate generation-conditional `operator/state.json` stores exact root files, saved binary plans, HMAC key, history, before-state captures and uncertainty/readback receipts. It excludes provider caches, credentials and any local Terraform state. Names, file types, private permissions, size, source and history are checked on restore. A generation-conditional `operator/lock.json` serializes plan/apply transactions independently of GitHub concurrency.

Before the first Terraform mutation, the existing `started.json` receipt must reach durable storage. If that write fails, apply cannot run. If the runner disappears or apply/readback is uncertain, the lock and receipt remain; native GCS retains the latest Terraform state. Neither rerunning the job nor a new dispatch can replay that apply. Handled pre-apply failures may release the operator lock only after preserving their history. A previously existing Terraform state without matching operator history is never adopted. When protected main advances only application/docs, byte equality of the transport, operator/helpers, workflow and Terraform root permits a recorded source transition and a fresh plan. All prior plans become invalid. Any changed infrastructure policy requires a separately reviewed state/source migration; it is never inferred from a successful application merge.

After an uncertain operation, use read-only GitHub `observe` and an administrator-reviewed private resource inventory. The administrator must reconcile actual cloud operations, native state and both locks before approving any recovery; do not delete a marker, force-unlock a possibly live Terraform process or replay a stale binary. The transport deliberately provides no automatic lock expiry or recovery mutation. An exceptional reconciliation is separate from ordinary plan/apply and is not an instruction to return to owner-mediated Cloud Shell.

## Activation sequence

Install only the reviewed operational source through protected integration before using this lane; do not merge the held application merely to obtain a workflow. Complete the coordinated bootstrap approval and bindings, then dispatch `observe` and `plan` from the exact current operator SHA. Review the complete private plan, selected cost assumptions, source, stage, state, configuration, changed resources and emitted approval digest. Only the applicable explicit approval authorizes `apply`; GitHub's environment gate and exact digest enforce that boundary.

The first actual plan is closed `foundation`, without worker federation or funded trial. Existing `services` then `edge` progression remains mandatory. Application DEV acceptance, protected application integration, integrated TEST acceptance and separately approved exact-manifest production promotion remain in that order. This workflow does not fund AI, enable external invitations or promote production.

Credential-free tests cover separate-runner plan/apply, remote-state survival, failed write-ahead persistence, wrong approval, state drift, missing history, unsafe snapshots, and rejected non-main/retry identities. They do not establish installed WIF, IAM, DNS, OAuth, cloud provisioning or live acceptance.
