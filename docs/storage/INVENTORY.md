## Operational inventory procedure

Reuse commit `a035e4dfc5a28fb1018c624ba7693dea3c4608ab`, helper `scripts/deployment/inspect_jems_storage.py`, SHA-256 `fa4b93a33c1cccfe9be74f14bc9fffe85d1b092647943f380d93ac3decabbc31`. [The existing handoff](../operations/COACH_RELIABILITY_RELEASE_CONTROL.md#concrete-inventory-handoff) is authoritative; no new cleanup command is introduced. At future authenticated access, verify the checksum, obtain private disk/inode/process/worktree/reference metadata, classify unknowns KEEP and review exact candidates. Never delete active/rollback images, release journals, receipts, shared Git objects or unknown private files. No current-session claim that the historical 16 fixture tests were rerun. Repository and static asset cleanup belongs to the other workstream.

Prepared recovery points (`server/storage/recovery-points.ts`) add exact supplied-source chunks and a final hash-verified manifest to the disabled continuity store. Authority is the explicitly captured scoped snapshot; format `jems.recovery-point.v1`, ≤32 source keys and ≤16M UTF-16 units per source, ≤32k units/chunk. Writes/readback are incremental within one point, with idempotent receipts; different points can duplicate chunks. No expiry, delete or scheduler exists. Incomplete points are not published; corrupt/missing chunks stop reconstruction. Growth is source bytes × retained points plus metadata/receipts, with database operation amplification. Original art needs separately integrated private binary roots. No live snapshots were captured.
