# Storage migration, rollback and activation boundaries

This is the repository procedure for the combined November 25 candidate. The [completion register](../family-beta/COMPLETION.md) owns requirement dispositions and exact-source acceptance. The [nine-stage activation runbook](../family-beta/ACTIVATION.md#nine-stage-activation-plan) owns future cloud operations. Neither document authorizes provisioning, protected merges, paid calls, real-data migration, invitations or deletion. Routine work uses protected Actions and authenticated APIs; Cloud Shell is not an ordinary prerequisite.

## One authority per domain

The normal build retains existing source formats. The explicitly selected `storage-preview` build can prepare native games, Studio notebooks and Creation records through the existing application and Parent recovery controls. A query string, a persisted marker or beta participation cannot activate this build mode. Preparation is an explicit operation; application adapters select a prepared domain only after its verified completion marker exists. A partially migrated domain remains on its original source.

`NativeWorkspace`, `NotebookWorkspace` and the Creation adapter preserve existing domain validation and owner identity. Native pages load bounded project metadata and selected revisions. Notebook pages load cards, while exact selected conversations follow retained chapter links. Committed presentation summaries supply maker progress, guidance and notification state without pretending a metadata card is a complete conversation. The notebook cache contains the foreground session and at most eight unresolved jobs. Large session/chapter payloads are immutable, hash-verified chunks; they retain exact messages, design and provenance.

Notebook mutations are awaited. A source callback is staged against a validated owner snapshot, then only changed pointers and the new summary/head commit atomically. Reward facts and source evidence publish after commit. A prepared notebook transaction can join native changes in the same scoped IndexedDB transaction. One validated mutation snapshot may be reused only for the exact committed head and within an 8 MiB encoded-source bound; a changed head or detected corruption discards it. Explicit snapshots and restore verification reread originals. Cold mutations still reconstruct the bounded owner notebook; every mutation validates the proposed result and computes presentation projections. That write CPU cost, decoded cache memory and retained immutable history are explicit tradeoffs; bounded reads do not imply constant-time writes or reduced total retained bytes.

The [inventory](INVENTORY.md) distinguishes these integrated domains from still-existing whole-key profile, learning and evidence sources. Do not describe a domain as migrated because a generic record store exists. A complete recovery export resolves every active authority rather than reading a stale legacy key.

## Preparation, compatibility and rollback

1. Capture a complete verified recovery point before any separately approved real migration. Preserve exact owners, IDs, original artwork, engine versions, pending receipts and provenance. Synthetic preparation is engineering evidence only.
2. Hold the existing origin writer lock and same-tab source maintenance through preparation. Pin the original source string/hash and current profile. Read source data once, validate it, commit resumable bounded batches, and verify reconstructed records. A final source reread must match before publishing authority. Quota, corruption, changed source, revoked scope or incompatible data stops without deleting originals.
3. Keep legacy strings and every previously retained immutable version. Reload after successful preparation so old in-memory readers cannot continue writing a legacy source. Never dual-write competing authorities or acknowledge an asynchronous save before its durable commit.
4. Use only readers that understand the written schema and domain activation. Clearing an activation marker is not a rollback after new-format writes: it would reopen an outdated original. Repair forward or explicitly restore a reviewed compatible recovery point. Unknown fields, missing chunks and conflicting immutable IDs remain visible failures; do not truncate them to satisfy an older reader.
5. Verify actual application startup, library/open/save, pending receipts, parent reports, rewards, export, restored games, quota and interruption. Run the same actual-application fixture before and after, including serialization and retained-byte costs. Adapter-only throughput is insufficient.

An owner profile is local-origin scoped. An Adult source retains its exact `adult:<device UUID>` identity; a new trusted device receives a separate identity. Restoring to that new identity requires the explicit mapped private recovery procedure below. Cloud synchronization separately maps to the server-issued family/profile scope; neither local origin hashes nor client family IDs grant remote access. Adult recovery still requires a fresh grant.

## Local journal and compound saves

Legacy Studio create/copy operations use the existing reversible journal for exact workspace, notebook and optional profile images. Pending means restore original strings; committed means finish committed strings and cleanup. Compare every captured value with its old/new image before touching any. Unknown/newer bytes, malformed journals and scope mismatches block ordinary writes. An intent-persistence failure changes no source; interrupted cleanup after the commit marker does not report lost work.

Prepared native/notebook changes can share one IndexedDB transaction. Where a compound operation still includes a legacy profile image, its retained intent and startup recovery bridge that explicit cross-store boundary. Do not call a sequence across localStorage and IndexedDB a single browser ACID transaction. Existing writer-lock, maintenance and recovery checks remain required.

Preserve corrupted originals for private recovery export. Do not clear a journal or discard an unavailable asset simply to make startup succeed. Recovery validates the entire covered set before replacement and keeps the original recovery point through acceptance. Browser persistence does not guarantee survival of device loss or origin eviction.

## Authenticated private continuity

The gateway mounts same-origin `POST /v1/storage/{status,commit,lookup,read,changes,page}` behind current family/device/session checks. Operator configuration and current guardian consent select explicit data categories; absent configuration is off. Local-only participation produces no continuity upload. A status epoch binds the current grant, notice, policy and guardian approval; withdrawal, renewal, revocation or profile change invalidates in-flight work.

A record operation has an opaque stable identity and expected versions. Server transactions atomically publish current records, immutable history, reference-only feed/index metadata and receipts. Receipt lookup resolves a lost acknowledgment. Local durable ordering, receipt replay and separate local/server version mapping preserve unuploaded edits and reject stale remote replacements. Conflict handling retains both meaningful histories and requires an explicit choice; wall-clock timestamps never authorize last-write-wins. These operations do not wrap a paid build, coach request or uncertain remote-fork POST.

The integrated application transfer surface is scoped to supported native saved-game graphs. Original-art dependencies need the complete recovery path until that continuity mapping is supported. Generic authenticated feed/tombstone support is not a claim that every local domain is automatically synchronized. Native tombstones remain held for reviewed removal; no automatic physical asset deletion or retention deadline is introduced. Domain mappings and any remaining limitations are recorded in the completion register.

## Immutable assets and decoder order

Split private-game encoding remains off by default. The v2 manifest separates unchanged original asset strings and compiled code while retaining complete small metadata/configuration snapshots. Hash identity is bound to the existing workspace and family/Adult audience. Identical assets from unrelated audiences are not pooled. Reconstruct and validate exact source/code/assets before runtime use; missing or corrupt dependencies fail closed. Existing inline and whole-object encodings remain readable.

Deploy compatible readers before authorizing v2 writes. Keep a compatible decoder for rollback; an old decoder cannot safely consume newly written manifests. Failed uploads may leave immutable orphan objects, but metadata must not commit broken dependencies. Reference tracing returns incomplete for unknown or missing roots. It is a dry run, not deletion authority or a complete bucket inventory. Retained games, jobs, backups, rollback points and original masters must all remain roots.

## Complete recovery and future cloud operation

Parent recovery captures profiles/progress, active native/notebook/Creation records, conversations, learning/evidence, rewards, Pals and original drawing/rig/draft bytes. Immutable chunks are checksummed; the manifest publishes last. The graphical flow lists bounded recovery-point pages, previews the selected point, preserves a complete rollback point, then replaces through the coordinated recovery journal. Duplicate point receipts do not erase work created after an earlier successful restore. A new deliberate Parent preview/restore creates a durable attempt to repair a later independent loss from that same point; an interrupted attempt reuses its original identity across reload. Missing originals, mismatched owners/origins, corrupt chunks and unsupported schemas stop replacement.

Complete archives identify prepared records with the versioned `prepared-domains` part. The compatibility progress envelope retains the valid legacy snapshot; authoritative native, notebook and Creation sources remain separately validated per owner. Do not concatenate them through the old shared 50-game, 80-notebook or 40-scene limits. `completeSources()` resolves the actual owner sources for verification. Ordinary legacy complete copies remain readable and restorable in the normal build. A prepared copy requires `storage-preview`; the normal build refuses its restore before mutation because its application readers deliberately do not select prepared authority. A stored marker or imported file never enables that build mode. The preview's old progress-export button directs the grown-up to the complete-copy controls, avoiding a stale legacy-only export.

An explicit prepared restore on a compatible fresh target initializes the covered indexed domains from that target owner's retained baseline, then restores the scoped originals. Legacy validators and original strings retain their existing limits and bytes. Native indexed recovery validates the full owner graph independently of old aggregate counts, but an atomic native restore remains bounded to 5,000 record changes and 32 MiB. Exceeding that transaction bound fails without partially applying that native transaction. Creation and notebook retain their current per-owner domain limits. This is bounded recovery, not a claim of unbounded libraries.

The complete restore's full reward/source before-image journal lives in the existing recovery vault's IndexedDB `settings` store. localStorage holds only a small origin/namespace-bound journal pointer. Committed state is read from that indexed journal during startup; a reload alone is never evidence of successful restoration. Where every covered owner uses prepared authority, retained legacy native/notebook/Creation strings are neither rewritten nor duplicated into the journal. Before capturing that safety point, recovery may add verified missing original images/rigs from the selected archive so a missing referenced picture cannot prevent its own restoration. This additive repair never replaces existing image bytes, movement versions or active pointers. The complete before-point remains available. Interruption restores protected original heads and progress across the covered stores; additive immutable versions and pictures remain retained. An incomplete operation does not become a completed receipt merely because its imported originals are present.

The local vault protects against an individual source record being removed, not loss of that browser. Download remains available. The prepared cloud route and scheduler require explicit operator/guardian domain authorization, current parent recovery access and a separately approved schedule. A configured scheduler does not prove an operating cloud service. Schedule, retention, RPO/RTO and erasure exclusions remain reviewed configuration; this work invents no deletion deadline and activates no resources.

For actual household origin transfer, follow the one [activation runbook](../family-beta/ACTIVATION.md). Preserve every original browser partition, the authoritative server workspace, mapped source/destination identities and rollback copies. A transfer receipt permits reading its specifically mapped source recovery namespace; it never grants another family or Adult audience.

## Private Adult recovery after household transfer

The owner-household route is independently off unless `householdRecovery.enabled` is true with all required storage domains on the protected household gateway. `adultMappings` names the exact source HTTPS origin, source Adult audience and target Adult audience. The server validates current trusted-device membership, the fresh Adult HttpOnly cookie and this tab's current proof on every operation. External-family participation and guardian consent never grant this owner lane. No recovery file contains or restores those credentials.

The browser must also hold the verified one-hop household transfer receipt matching family, workspace and source/target origins. In a freshly opened destination Private parent session, review the earlier **Workshop game copies** first. If no source point exists, the explicitly selected **Save earlier workshop originals** action captures the retained mapped source audience with its original origin; it does not require the retired gateway to support this new route. Recover the original server-owned source/code/assets and their attestations; arbitrary client-uploaded compilation claims are not eligible. Only completed server restoration supplies the revision/project mappings used by **Review transferred private copies**. Local restoration refuses dangling remote originals, rechecks the mapping and fresh grant, preserves the unchanged source archive and namespace, and creates separate deterministic picture identities with identical original bytes. Source checksums remain provenance; they are not rebound as target authority.

Cross-audience or cross-origin generated copies are playback-only. Generation admission rejects editing those recovered IDs before any reservation, including after copying/forking them, so a new project ID cannot reset the owner's cumulative $5 premium lineage. Accounting, jobs, grants and spending allowances are never imported. An unfinished request remains in its original private copy; its destination notebook is read-only and does not restart that operation. Every explicitly reviewed local or workshop restore persists a scoped attempt identity before sending, retains it through an uncertain response or reload, and clears it only on a matching completed receipt. A later deliberately reviewed attempt can repair subsequent asset loss without treating the earlier receipt as proof that the bytes still exist.

Private recovery rows and previews clear when leaving the Adult workspace, including late completion of an earlier read. Missing consent, expired grants, missing/corrupt assets, unsupported formats and mapping changes stop the operation and retain originals. Synthetic phone UI and server fixtures are evidence for this source implementation; they do not establish an operating cloud backup, a real household migration, physical-device acceptance or permission to activate it.

## Imported identity compatibility

The opt-in native-game and scene adapters retain the existing record namespace: alphanumeric-first identifiers using letters, digits, underscore, colon or hyphen, with a maximum length of 160 characters including a per-project collection prefix. Application-generated UUID identities, and documented v1 games with those project identities, are covered by the migration tests. Older imported workspaces can contain identifiers accepted by their legacy readers but outside this narrower namespace, including dots or spaces, or scene identifiers too long for the prefixed collection. Preparation refuses those inputs without publishing an indexed authority; the original local-storage bytes and legacy reader remain available. A separate reviewed identity mapping is required before migrating those imports. This is a compatibility limit, not permission to rename or discard their originals or widen the remote identity contract.
